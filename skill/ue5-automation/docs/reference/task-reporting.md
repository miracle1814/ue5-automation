# 任务上报与任务级撤销（完整版）

> 从 SKILL.md §3.9/§3.10 迁出（v4.6 分层）。硬规则仍在 SKILL.md。

## 任务上报 SOP — 让人看得见你的意图与进度（agent 必须遵守）

> 数据源纪律：管理端（任务指挥台）的「KPI 条 / 任务档案四段」全部来自本节
> 上报。**不上报 = 用户什么也看不见**（面板只显示引导态，绝不编造）。纯主机
> 侧记账，零 UE 依赖，代价可忽略。
>
> **上报时点**（用户《可视管理需求.txt》口径）：与用户聊清需求细则之后、
> 开始驱动工具之前，就调 `ue5_task_begin` —— 管理端此刻出现，第一屏是
> 需求回显，用户发现理解偏差可当场纠正，避免返工。

**① 任务开始**——`ue5_task_begin`：

| 字段 | 要求 |
|---|---|
| `goal` | 必填，**用户口语**一句话（如「给传送门加进入提示」，不要写技术术语/资产名堆砌——任务列表直接展示它） |
| `asset` | 主目标资产路径（有则填） |
| `understanding` | **需求确认书**：与用户对齐的要点清单（分行/分号列出），不是给自己看的笔记 |
| `approach` | **实现逻辑**（见下方写法规范——用"操作逻辑"语言，禁止 API/工具名） |
| `steps` | 计划步骤 = 实现逻辑的逐条展开 `[{name, hint}]`（3-8 步） |

**写法规范（最重要）**——`approach` 和 `steps` 必须用**用户的操作逻辑语言**，
让不懂 UE 的人看懂"你要怎么把这件事做成"。禁止出现 API 名、工具名、截图
等执行器细节——那是手段，不是思路：

```
❌ 错误（API 流水账）：
   approach: "先拍改前基线 → set_actor_transform 移到(814,519,60) →
              project_actors_to_screen 验证 → 拍改后对比图"

✅ 正确（操作逻辑）：
   approach: "先查清石柱现在在场景的什么位置 → 算出它该去的新位置
              （画面正中央对应的地面点）→ 把石柱搬过去 → 读回它的坐标，
              确认真的到位了"

   steps: ["找到石柱的当前位置", "算出目标落点", "把石柱移过去",
           "读回坐标确认生效"]
```

截图、读回比对、命令选择是**每个逻辑步骤内部的执行细节**——挂在步骤的
note 和 evidence 里给用户当证据，不要上升为独立步骤。

**② 过程中（每个逻辑步骤，可多次上报）**——`ue5_task_step`：

> ⚡ **从 v3.9 起，这一步可以很轻**：编译诊断 / 整图写入 / 截图等关键工具调用
> 会**自动**记入当前进行中步骤的过程日志（含耗时），并在你没上报任何进度时
> 自动把第一步置为进行中；收尾时未完成的步骤自动封口（标记 `auto_closed`）。
> 因此**最少只需 `task_begin` + 干活 + `task_end`**；手动 `task_step` 用于：
> 标记步骤完成/失败、写关键结论、附证据。
- `step_id` 按计划定位 + `status: running|done|failed|skipped`；
- 同一步骤的多次上报会**追加**为该步骤的过程日志（时间线展示中间过程），
  例如定位步骤："查到石柱在 (200,-500)" → "确认它当前在画面左边缘"；
- `note` 一句话结果（业务语言）；
- `evidence` 带证据，**改前/改后用配对形态**：
  `"evidence": {"pair": {"before": "shot_x.png", "after": "shot_y.png",
  "caption": "这一步改了什么、看对比该注意什么"}}`；
  非配对证据用 `{"screenshots": [路径], "errors": n}`；
- 撞错时 `ue5_task_error` 一句话记"做了什么→错在哪"（复盘素材）。

**③ 收尾**——`ue5_task_end`（交付物与验证是**给人的最终交付**）：

> 表达分层纪律（v3.11）：**工具负责事实，你负责人话**。
> 工具会自动记账（命令流水/资产路径/编译结果，准确但机器味）；
> 你必须用自己的话把「改了什么 · 为什么 · 怎么确认」讲清楚——
> 用户看的是你的表达，面板把工具事实作为可核查的凭据并列展示。

- `deliverables`：`[{kind, path, action, note}]`，`note` 必须写三要素
  「**改了什么 · 为什么 · 怎么确认**」，例：
  `{"kind":"蓝图资产","path":"/Game/BP_Door","action":"modified",`
  `"note":"把重叠事件接到打印提示，让玩家走进门有反馈（原来没反应）；"
  "打开该蓝图看 EventGraph 首条连线即可确认"}`；
- `how_to_verify`：**用户视角的步骤**（字符串或数组），不含命令名/参数，
  例：「打开 BP_Door → 看 EventGraph 有『重叠→PrintString』→ 点 Compile 无错
  → 拖入关卡 Play 碰一下，屏幕打印」；
- 不填时工具会从命令流水自动汇总（标注「自动汇总」），但**可读性差于你写的**——
  能填就填。
- `status: success|failed|aborted`；
- ⚠️ **success 需证据**：本任务没有任何编译诊断/整图写入/截图记录时，
  收尾会被打 `unverified: true` 并在管理端显示「⚠ 未验证」徽章（结论视为
  agent 自述，需人工复核）——先跑一次验证再声称成功；
- `summary`：实现了什么（功能级，不是步骤级）；
- `lessons`：经验分析——有无判断错误的步骤、下次怎么避免简单问题复杂化、
  可归纳进下一次实操规划的新方法（面板复盘卡直接展示给用户）。

**硬规则**：同一时刻一个任务（`task_begin` 会拒绝并行）；失败重试标同一
`step_id` 而不是新开步骤；完成后**必须** `task_end`（挂着不收 = 用户看到
永久"进行中"）。

## 任务级撤销 — 用户说"撤回"时怎么撤（v4.5 · 需 v4.5 版 DLL）

写命令会**自动**在 UE 原生事务栈里各留一步（标题 `[agent] <命令> <资产>`）；
你不需要手动 begin/end，也不要自己反向操作去"撤销"。

**命令**（白名单 84 → 86）：

| 命令 | 用途 |
|---|---|
| `agent_undo_status` | 读状态：`agent_undoable`（栈顶连续 agent 步数）、`next_title`、`next_is_agent` |
| `agent_undo{count}` | 连续撤销最多 count 个 agent 步；遇非 agent 步立即停并给 `stopped_reason` |

**标准流程**：

1. 用户说"刚才那步不要了 / 撤回这个任务" → 先 `agent_undo_status`；
2. `agent_undoable > 0` → `agent_undo{count: N}`（N 由用户意图决定；不确定就一步步来）；
3. 看返回：`undone` 是实际撤掉的步数，`titles` 是撤掉的事务标题；
4. `undone < 请求数` 时**必须**把 `stopped_reason` 用人话转述给用户
   （最常见："中间你手动改过，回滚停在你那步之前"）；
5. `agent_undoable == 0` 且 `redo_count > 0` → 说明刚撤过，可提示"要不要重做"
   （重做用编辑器 Ctrl+Y，本工具不代劳）；
6. 撤销后如需继续做，重新执行写命令即可（会生成新的事务步）。

**边界（必须向用户讲清，不要含糊）**：

- 资产创建/删除**不在**撤销栈：回滚不会删掉新建的蓝图，也不会恢复删掉的资产；
- 用户在 agent 操作之间穿插的编辑会让回滚**提前停**——不跳过、不误撤；
- 面板只读：它显示"可回滚 N 步 / 已回滚 N 步"，但**不提供按钮**；
  回滚永远由你（agent）执行；
- 旧 DLL（早于 v4.5）调用 `agent_undo_status` 会 fail-loud 提示重新编译，
  不要用 Python 侧逻辑"模拟撤销"。

**硬规则**：不要为了让撤销"看起来有效"而先撤再重建——重建是另一组新步骤，
会让用户更糊涂；撤销后如实报告，然后按用户意愿重新做。
