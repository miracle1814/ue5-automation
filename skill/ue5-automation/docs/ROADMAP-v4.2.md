## 二、必须承认的三处认知错误（v4.1 判断有误）

| 编号 | v4.1 的说法 | 事实 | 影响 |
|---|---|---|---|
| **E1** | "双引擎 5.1+5.8 是最大差异化" | UEBox 覆盖 **5.0–5.8**，比我们更广 | 该优势**不存在**，不能作为卖点 |
| **E2** | "任务级审计是独占" | UEBox 有 `reviewChanges`（每轮列新建/修改/删除）+ `writeLedger` + 资产锁 | 我们不独占；但**"交付物 + 你怎么验证"仍是它没有的** |
| **E3** | "编译诊断自愈是护城河" | UEBox 用 **C++ `FCompilerResultsLog` + `FUObjectToken`→`UEdGraphNode` 拿结构化诊断**（精确到 NodeGuid + 子图路径），我们靠**解析中文日志文本** | 我们**精度低一档**；中文引擎支持是我们唯一可能领先处，但未验证优于它 |

**结论：目前我们真正独占的只有**——①"交付物清单 + 用户怎么验证"这一层面向交付的表达；②轻量（无 Electron、可寄生任意 AI 客户端）；③开源桥可被自己二次开发。

## 三、实用性红黑榜（诚实盘点自己）

用户要求：不做华而不实的东西，不把时间花在实用性不大的功能上。按此标尺给已做功能分级：

### 🟢 真刚需（继续投入，值得投入）
| 功能 | 为什么实用 |
|---|---|
| `verified` / `compiled` 硬信号 + fail-loud | 让"改好了没"有客观答案，是整个工具的地基 |
| 中文编译诊断（5.1/5.8 双变体）+ 收敛判据 | 中文引擎用户唯一能用的诊断，竞品未覆盖 |
| 交付物清单 + 分步验证指引 | **竞品没有**：用户拿到就能自己验收，不依赖信任 |
| 未验证徽章 | 防 agent 自述成功，企业采用的必要条件 |
| 截图三源 + 机位溯源 | 视觉自检的全部价值 |
| 移植包 + 25 项自检 | 新机 5 分钟可用，直接决定试用率 |
| 命令流水（含 UE 内动作） | 技术用户排查问题的唯一入口 |

### 🟡 半实用（有导航价值，不再加码）
| 功能 | 判断 |
|---|---|
| 5 段阶段轨道 | 有导航价值，但当前已够用，不再美化 |
| 原话 vs 我理解成 | 防误解有价值，保持 |
| 任务列表筛选/证据角标 | 小工具，保持 |
| 完成提醒（S7） | 0.3 人天，顺手可做，不必单独立项 |

### 🔴 装饰性（**停止投入**）
| 已投入的 | 判断 |
|---|---|
| 动效（入场/悬停/脉冲）、KPI 计数动画、灯箱微交互 | 主观体验加分有限，不再迭代 |
| 字号阶梯/字号精修、渐变/水印、emoji 图标 | 一次性做过即可，不再当任务 |
| 图结构 diff（v4.1 的 S4，3 人天） | **炫技**：用户要的是"编译通过 + 截图对"，不是节点级 diff |
| 提示词模板库（S6）| 有价值但**纯文档**可解决，不必做进面板 |
| 命令流水人话化（S8）| 只对非技术用户有价值；我们的用户是开发者，优先级低 |
| 性能剖析（S10）/ 工具数量扩张（S11）/ 跨平台（S12）| 与"蓝图自动化 + 可信交付"定位无关，明确不做 |

## 四、从 UEBox 源码里学到的 6 个"实用刚需"（我们缺，且成本可控）

| # | 学什么 | UEBox 怎么做 | 我们的实现方案 | 成本 | 为什么实用 |
|---|---|---|---|---|---|
| **A** | **保存闭环检查** | 要求保存却没存上时第一句就警告"改动只在内存里，关编辑器就没了" | `task_end` 校验：本任务写过的资产若 `is_dirty` → 明确警告 + 自动 `save_asset`（可配置） | **0.5 人天** | **今天真实踩坑**：BP_Door 重启后消失，工具完全没提醒 |
| **B** | **死循环保护** | `loopBreaker`：同工具+同参数连续失败 2 次拦截（编译放宽 5 次），成功则清零 | 桥端中间件统计"工具名+参数哈希"失败次数，超限直接返回"停止重试，换方法" | **1 人天** | agent 反复撞同一个错误会烧钱且破坏信任 |
| **C** | **任务级撤销** | 插件把 `GEditor->Trans` 换成 agent 独立事务栈（"AI 的三十步不会埋掉你的撤销历史"） | 阶段1：任务开始时**文件快照**任务涉及资产（.uasset 复制、>200MB 降级提示）；面板「回滚本任务」 | **2 人天** | 用户不敢让 AI 动重要资产的根本原因 |
| **D** | **高危审批（简化两档）** | 三档 ask/auto-edit/yolo + 风险三值 + 按参数降险 | 只做两档：`mutating` 放行、`destructive`（删资产/force 替换/批量）**必须批准**；面板批准卡片，60s 超时拒绝 | **2.5 人天** | 误删风险→0；也是作者自己承认的软肋 |
| **E** | **资产锁提示** | 插件端角标"AI 正在改这个资产"+用户动手时提醒 | 任务期间展示"正在操作资产清单"；写操作前检查资产是否被外部修改 | **1 人天** | 用户和 AI 同时改同一蓝图 → 互相覆盖 |
| **F** | **结构化编译诊断（C++）** | `FKismetEditorUtilities::CompileBlueprint` + `FCompilerResultsLog`，从 token 拿 NodeGuid/子图 | 给 C++ 桥加 `CompileAndDiagnose` UFUNCTION，返回 `compiled/error_count/diagnostics[{node_guid, graph, message}]`；Python 侧优先用它，日志正则降级 | **3 人天**（含双引擎重编） | 精度：日志正则 vs 引擎原生结构化，差一档 |

**备注 F**：这是唯一需要改 C++ 并重编双引擎的项，但收益明确（诊断精度 + 去掉日志时序依赖）。建议放 P1，而非 P0。

## 五、修订后的计划（实用性优先）

### P0 —— 立刻做（4 人天，5 项）
| 项 | 交付 | 验收标准 |
|---|---|---|
| **A 保存检查** | `task_end` 校验脏资产 + 自动保存（默认开，可关） | 写图不保存直接结束 → 明确警告"未保存"；再次打开编辑器资产仍在 |
| **B 死循环保护** | 中间件按"工具+参数"计失败，超限拦截 | 同一错误参数连续调用 2 次 → 第 3 次被拦并提示换方法 |
| **C 任务级撤销** | 任务开始快照 + 面板「回滚本任务」 | 改坏蓝图 → 一键回滚 → 与任务前一致 |
| **D 高危审批（两档）** | destructive 操作挂批准卡片 | 删资产/force replace 前弹卡；拒绝则不执行 |
| **E 资产锁提示** | 任务卡显示"正在操作的资产" | 面板可见当前任务触碰的资产清单 |

> 这 5 项全部有 UEBox 源码验证（它做过）或我们今天的真实踩坑，**没有一项是猜的**。

### P1 —— 两周（3 人天 + 3 人天）
| 项 | 交付 | 验收 |
|---|---|---|
| **F C++ 结构化诊断** | 新 UFUNCTION + Python 优先路径 + 日志正则降级 | 5.1/5.8 真机：诊断含 `node_guid` + 子图，修复循环仍 2 轮收敛 |
| **G 交付物自查** | 交付物自动补"未验证项"（没编译就标黄） | 无编译记录的任务 → 交付物区显示"未验证编译" |

### P2 —— 视情况（不建议现在做）
- 完成提醒（0.3 人天，顺手）
- 会话保活/重连（2 人天，只在长任务场景有用）
- PIE 多帧采样（1.5 人天，竞品有；我们单帧够用）

### ❌ 明确删除（不再投入）
图结构 diff · 提示词模板面板 · 命令流水人话化 · 性能剖析 · 工具数量扩张 · 跨平台 · 更多动效

## 七、和 UEBox 的关系：不打正面，打两个它公开承认的软肋

作者在 Epic 论坛公开征集"硬核反馈"，点名两个方向——**这正是我们的靶心**：

1. **"蓝图图仍会出错"** → 我们的靶：**把"编译诊断 → 修复收敛"做到比它更稳**
   - 我们已有的：中文双变体日志、收敛判据分离、错误刷盘重读
   - 我们要补的：F（C++ 结构化诊断）+ B（死循环保护）→ 让"改到通过"从"能"变成"稳"
2. **"Agent 操作不安全"** → 我们的靶：**审批 + 撤销 + 资产锁 + 未验证徽章**
   - 这就是 P0 的 C/D/E + 已有的 verified/compiled

**一句话**：UEBox 是完整产品（Electron + 100 工具 + 多模型），正面比不过也不该比；我们做的是**"能装进任何 AI 客户端的可信执行层 + 可交付审计"**，把它的两个软肋做成我们的两个强项。

## 八、执行建议

**建议顺序**：A（0.5d）→ B（1d）→ C（2d）→ D（2.5d）→ F（3d）。
A/B/D 可以一天内做完（1.5 人天就能见效果），C 需要设计快照策略（2 天），F 需要改 C++ 并重编双引擎（3 天，可放周末跑编译）。

**先做 A+B 的理由**：成本 1.5 人天，直接消除"改完丢了"和"反复撞墙"两个最伤信任的问题，且不需要改前端架构。
